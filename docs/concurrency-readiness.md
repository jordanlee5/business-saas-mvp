# 集中领取、兑换压测与扩展准备

2026-11-05，开发基线 `58eef7383f3e4163add6c3b705d0767420052ba1`。会员数量尚不确定，用户要求先发现瓶颈再选择服务器。全程虚拟会员、虚拟商品和隔离数据库；未部署公网服务器，未提交微信审核。

## 后续对照：4,000 个 SKU、100 并发浏览

从 `96003b7` 接续，使用同一 PostgreSQL 16 和应用镜像，将容器资源上限配置为合计 4 CPU/8 GiB 与 8 CPU/16 GiB。前者应用与测试端共享 3 CPU/6 GiB、数据库 1 CPU/2 GiB；后者分别为 6 CPU/12 GiB 和 2 CPU/4 GiB。均为单个应用进程，先完成 4 核组，再完成 8 核组，不与回归测试同时运行。

**宿主限制：** 运行后核对 WSL2 只有 7,835 MiB 实际内存（另有 2,048 MiB swap），可见 20 个逻辑 CPU。设置容器 16 GiB 上限不会创造实际内存。因此以下只能作为 CPU 配额增加的初步对照，不能视为真实 8 核/16GB 云服务器或内存翻倍的验证。测试中未采样内存使用峰值。

400 件商品，每件 10 个 SKU，共 4,000 个 SKU。每页 20 件商品，轮换访问 20 页；沿用虚拟商品种子，仅一个规格具有已入库库存，其余无库存余额行。本轮测小程序公开商品列表接口，不含后台 SKU 表格渲染、商品详情全部规格、图片文件下载或兑换写入。每档重复 3 轮，两组各 3,330 个测量请求全部返回 200，无数据库错误。

| 浏览并发 | 4 CPU 上限组：三轮 P95 的中位数 | 8 CPU 上限组：三轮 P95 的中位数 |
| --- | ---: | ---: |
| 25 | 721.40 ms | 727.05 ms |
| 50 | 1,715.38 ms | 1,643.86 ms |
| 100 | 3,439.44 ms | 3,563.28 ms |

100 并发时，4 核组三轮 P95 范围为 3,435.18～3,876.72 ms，8 核组为 3,367.83～3,778.10 ms；范围重叠。三轮吞吐中位数分别为 75.94 和 75.72 请求/秒。**这组测试没有显示提高 CPU 配额有明显收益，16GB 内存的收益尚未测得。** 两档都能完成该批次，但 100 并发时尾部请求要等待约 3～4 秒，不能直接作为正式环境响应承诺。

这些是本机 WSL2 容器的资源上限，不是两台真实云服务器，也不表示内存实际占满。客户端与服务端仍在同一 Python 进程，可能共同受到执行和调度限制。8 核组的 100 并发波次，进程 CPU 时间约为墙钟时间的 1.1 倍，尚无证据表明增加的核数被充分用于处理请求；具体应用热点还需剖析。此结论不能外推为更多内存、更多核数在混合负载或多进程下都无用。

复验命令为 `python -m tools.rehearse_concurrent_mall --postgres --catalog-only --products 400 --skus-per-product 10 --levels 1,25,50,100 --repetitions 3`，PostgreSQL 目标仍受下文全新虚拟 Docker 库保护。延迟不含客户端等待并发槽位的时间，未进行长时间稳定负载和互联网测量。

采购继续暂缓。先做共享后台会话与多进程准备，后续将负载端移到独立进程/主机，补图片、真实库存分布和 OCR 的混合负载，再判断 8 核/16GB 的价值。[本轮部署、恢复及容量证据](validation/postgres-staging-20261105.json)

## 首轮判断

**先补 PostgreSQL 测试部署，再定服务器。** SQLite 在集中兑换、取消时出现写入等待超时，提升机器配置不能替代数据库并发验证。下面保留从 `58eef73` 开始的首轮压测记录。随后从 `96003b7` 接续的小轮已增加独立的 [PostgreSQL 测试部署与恢复](postgres-staging.md)，原 `deploy/staging` 和 `tools/staging_server.py` 继续保留为 SQLite 测试包。两轮都没有迁移真实库，也没有宣称正式上线容量。

本轮实际修复两点：

- 商品列表由数据库汇总最低积分价和是否有货，减少每次读取整组 SKU 与库存对象的开销。停用供应商、停用规格、价格、分页和图片可见性保持原有规则，不缓存价格和库存。
- 同一领取凭据并发竞争，在另一请求已提交入账后发生唯一约束冲突时，返回原有统一不可领取提示（400）。其他数据库故障仍返回暂不可用（503），不把未知故障伪装成成功，也不泄露谁已领取。

## 场景和结果

100 件商品，每件 10 个 SKU，共 1,000 个 SKU；列表覆盖 5 页。并发档位 1、8、24、48，各档列表请求 60、60、72、144 次，各档独立凭据领取 8、16、48、96 次。另有 48 次竞争同一个未使用凭据，最终总计 169 笔入账。使用正常 600,000 次 PBKDF2 校验成本，未降低凭据保护强度。

48 个已登录会员各有 100 积分和自己的地址，通过配送告知预览后争兑同一规格的 24 件商品，每件 8 积分。成功方再次提交两次、再次取消两次，另用其他会员身份查询订单。各次重试使用原订单请求编号和原请求体；重试耗时单独计入，不抹掉首次 503。

以下为受限 Linux 容器中的完整对照轮次：

| 指标 | 原代码 + SQLite | 优化后 + SQLite | 优化后 + PostgreSQL |
| --- | ---: | ---: | ---: |
| 48 并发商品列表 P95 | 8,608.60 ms | 1,251.82 ms | 1,617.87 ms |
| 48 并发独立领取 P95 | 4,330.78 ms | 3,602.82 ms | 3,634.82 ms |
| 48 次同凭据竞争 | 1 成功、46 拒绝、1 暂不可用 | 1 成功、47 拒绝 | 1 成功、47 拒绝 |
| 首次 48 人争兑 24 件 | 24 成功、10 库存冲突、14 暂不可用 | 24 成功、10 库存冲突、14 暂不可用 | 24 成功、24 库存冲突 |
| 首次 48 次取消 | 35 正常、13 暂不可用 | 35 正常、13 暂不可用 | 48 正常 |
| 全部测量中的 503 次数 | 28 | 27 | 0 |
| 最终账目、库存与权限核对 | 通过（含重试） | 通过（含重试） | 通过（无需重试） |

SQLite 的两组失败请求按原请求重试后，14 次兑换均正常返回库存冲突，13 次取消正常返回。最终只产生 24 笔订单、24 次预占与 24 次释放，账户全部恢复 100 积分，库存预占为零，库存/积分流水与余额核对一致，其他会员查询返回 404。数据库记录到 27 次 `SQLITE_BUSY`；未出现超卖或重复发积分。

PostgreSQL 的兑换 P95 为 1,480.28 ms，取消 P95 为 1,719.87 ms。但 48 次同凭据竞争 P95 仍达到 6,209.37 ms，独立领取也存在校验计算与事务等待开销。后续需针对热点凭据的重复请求和突发领取继续检查限流与排队，不能把“没有 503”理解成所有响应都足够快。

Windows 本机的辅助对照也看到列表改善，48 并发 P95 从 2,578.82 ms 降到 937.01 ms。它未设置资源配额，与 Linux 数字分开保存，不混为一组容量结论。

## 测量边界

- SQLite 容器限制 4 CPU/8 GiB；PostgreSQL 组为应用与压测端合计 3 CPU/6 GiB，数据库 1 CPU/2 GiB，总量 4 CPU/8 GiB。两组资源分配不同，不是同规格单机数据库性能排名。
- WSL2 下 Linux 容器、Python 3.12.16；`cpu_count=20` 是宿主可见逻辑核数，实际限制以证据中的容器配额为准。
- 使用已有部署依赖镜像 `business-saas-staging-review:20261105`，把本轮代码只读挂载后复制到容器临时目录运行。压测不是对旧镜像内置代码的测量。无真实数据库、附件或微信秘密配置挂载；PostgreSQL 仅内部测试网络，不开放公网端口。
- 通过回环 HTTP 访问真实接口；客户端与服务端在同一进程，共用资源预算。有限批次、闭环并发，延迟不含客户端等待并发槽位的排队时间。请求吞吐包含业务拒绝，不能直接当作成功兑换吞吐。
- 微信换码使用虚拟响应，不包括真实微信限额/延迟、互联网、HTTPS、图片带宽、OCR 作业、长时间稳定负载或多实例。领取校验和真实数据库事务照常执行。
- 每组是一次完整测量，不提供统计置信区间。初次 Linux 测量曾因取消 503 停在断言处，随后增加显式重试并记录初始失败，重新完成对账；失败日志摘要也留在证据中。
- JSON 的 `result=PASS` 表示流程和最终一致性断言通过；是否存在 503 看独立字段 `availability_pass`，SQLite 明确为 false。进程成功退出也不代表已满足上线性能门槛。

## 重复验证

在安装项目依赖的仓库根目录启动全新 Python 进程：

```sh
python -m tools.rehearse_concurrent_mall --levels 1,8,24,48
```

默认只新建临时 SQLite，不读取应用原有数据库，不接受业务库路径。标准输出为最终 JSON，标准错误为分波次统计与初始化日志。不要使用 Python 的 `-O`，脚本需要断言完成对账；客户端连接错误与非预期状态会使演练失败。

PostgreSQL 演练仅供开发方在**新建、独立、可销毁的 Docker 测试环境**执行：

1. 建专用内部 Docker 网络，创建空白 PostgreSQL 16 容器；只在该网络提供别名 `database`。库名固定 `mall_concurrency_test`、用户 `load_runner`，密码随机产生，不写进命令记录或仓库。
2. 应用容器同网运行，通过进程环境传入 `MALL_LOAD_TEST_POSTGRES_URL`（`postgresql+psycopg`、上述主机/库/用户、5432 端口）和 `MALL_LOAD_TEST_ALLOW_RESET=1`，执行同一命令加 `--postgres`。不得复用应用的 `DATABASE_URL`。
3. 工具核对连接目标和空库后，迁移、生成虚拟业务、运行场景，结束后删除本次虚拟行并回退结构；核对只剩空迁移版本表。外层运行器还必须在失败路径销毁本次创建的容器、卷和网络；不得套用生产实例名称。
4. 保存容器配额、退出状态、是否 OOM 和最终 JSON。本轮实际配额见上表说明。目标限制有独立回归测试，错误目标在连接前拒绝。

该模式不是备份或迁移工具。正式数据不会因为设置测试标记就变成可销毁数据，必须始终使用刚创建的空白容器。
