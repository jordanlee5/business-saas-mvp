# M5-4 订单确认履约与原子消费出库

## 范围

M5-4 在 M5-2 订单原子预占及 M5-3 取消释放基础上提供内部确认履约领域服务。启用中的超级管理员和运营管理员可以把证据完整的 `CREATED` 订单确认进入 `FULFILLING`；`CANCELLED`、`SHIPPED`、`COMPLETED`、`REFUNDED` 及未知状态均失败关闭。已经处于 `FULFILLING` 且证据完整的订单可以安全重放。本切片不新增 HTTP 路由、会员端页面或管理员订单页面。

确认履约严格复用订单项、订单积分批次分配和原始 `RESERVE` 流水。每个积分批次追加一条 `CONSUME` 流水，把对应预占积分扣减为零；每个 SKU 追加一条 `OUTBOUND` 流水，同时扣减现存数量和预占数量。原预占流水、积分分配和订单快照不修改、不删除，消费及出库幂等键由订单编号与积分批次或 SKU 确定，不接受客户端提供新的业务键。

## 权限、原子性与审计

`execute_order_fulfillment()` 使用独立事务，SQLite 采用 `BEGIN IMMEDIATE`，PostgreSQL 使用行锁。订单状态、库存余额及流水、积分账户及批次余额、积分流水和管理员操作日志必须一起提交或一起回滚。较低层的 `fulfill_created_order()` 不提交，调用方遇到任何异常必须整体回滚。

确认履约使用新登记的 `mall_order_fulfill` 审计动作，只允许启用中的超级管理员和运营管理员执行。每个订单首次确认只生成一条管理员操作日志；重复或并发确认读取首次操作者及完整业务证据，不重复扣减积分、库存或新增日志。

首次确认前必须证明订单项积分、成本、数量合计，积分批次分配合计以及订单主记录完全一致，并逐项验证原库存和积分预占流水。`FULFILLING` 重放还必须验证所有 `CONSUME`、`OUTBOUND` 和操作日志存在且内容一致；缺失、额外、冲突或被篡改的证据都失败关闭，不自动补写。

## 积分与库存口径

积分 `CONSUME` 只扣减批次及账户的预占余额，不再次扣减下单时已经减少的可用余额。批次完全消费后若可用和预占余额均为零，则进入 `EXHAUSTED`；仍有可用积分的批次继续保持 `ACTIVE`。

已经在有效期内完成预占、但确认履约时越过原 `expires_at` 的批次仍可闭合该订单消费，且不修改原到期时间。这不会允许新订单使用过期批次。冻结批次不允许消费，必须等待解除冻结或由订单取消流程释放预占。

库存 `OUTBOUND` 按订单项数量同时减少 `on_hand_quantity` 与 `reserved_quantity`，保持可售数量不因“预占转出库”再次变化。余额、顺序流水或原订单预占无法互相重算时停止履约并回滚。

## 数据库影响

本切片不新增数据库迁移，继续使用 `0008_order_reservation` 已具备的 `FULFILLING`、积分 `CONSUME`、库存 `OUTBOUND` 和管理员操作日志结构。部署时不需要升级真实业务库，但仍须确认当前 revision 为 `0008_order_reservation` 且结构就绪检查通过。

## 明确不实现

本切片不实现小程序下单、取消或履约 API、购物车、地址、会员端订单页、管理员订单页、发货、物流录入、订单完成、退款、库存退回、供应商结算或真实测试数据。`FULFILLING` 仍不进入供应商结算。

## 验证

专项测试覆盖正常确认履约、积分与库存精确转换、批次耗尽、管理员权限、精确幂等重放、并发重复确认、取消订单拒绝、冻结批次整体回滚、预占证据篡改、履约证据篡改及原积分批次越过到期时刻后的既有订单消费。真实 PostgreSQL 集成测试验证行锁下并发确认只产生一套 `CONSUME`、`OUTBOUND` 与审计证据；由于没有结构变化，不执行新的 Alembic revision，仍核验当前 head/readiness 并运行全量回归。

M5-5 在此履约证据上继续推进手工物流和订单完成，见 [订单发货与完成说明](order-lifecycle.md)。
