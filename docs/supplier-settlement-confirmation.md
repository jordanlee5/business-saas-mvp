# 供应商结算原子确认说明

## 1. 本切片目标

M6-3 在 M6-2 待确认批次生成能力上增加内部领域服务，把证据完整的 `PENDING_CONFIRMATION` 供应商结算原子推进到 `CONFIRMED`。

本切片继续复用 `0011_supplier_settlement_foundation`，不新增数据库迁移，不开放 HTTP API、后台页面、支付、撤销或冲销。M6-4 已在此确认边界之上新增只读查询与已确认批次 Excel 审计导出，详见 [供应商结算查询与导出说明](supplier-settlement-export.md)。

## 2. 权限与状态

只有启用中的超级管理员可以确认供应商结算。运营管理员仍可生成待确认批次，但不能执行确认；初审、复核、上传方、停用、缺少级别或未知级别账号同样失败关闭。

首次确认只接受 `PENDING_CONFIRMATION`，成功后进入 `CONFIRMED`。对同一已确认编号的重复或并发请求执行精确重放，返回原确认人、确认时间和审计记录，不新增第二套事实。

## 3. 确认前证据复核

确认事务会锁定目标批次及来源订单证据，并重新验证：

- 批次的订单数、明细数、商品数量和人民币成本总额可由全部结算明细重算；
- 每条明细仍唯一对应原订单项，供应商归属、订单公开编号、完成时间、商品、SKU、供应商、数量和成本快照一致；
- 来源订单仍为 `COMPLETED`，没有退款原因或退款时间，完成时间仍位于批次左闭右开区间；
- 生成管理员、生成时间、生成描述与唯一 `mall_supplier_settlement_generate` 审计完整一致；
- 确认时间不得早于生成时间，待确认批次不得提前携带确认人、确认时间或确认审计。

任一状态、快照、合计、时间或审计证据漂移时只报告错误，不自动修复，也不写入部分确认事实。

## 4. 原子写入与并发

首次确认在同一事务内写入 `CONFIRMED` 状态、确认管理员、确认时间及唯一 `mall_supplier_settlement_confirm` 管理员日志，随后回读生成与确认两组证据；核验通过后才提交。

SQLite 独立执行入口先取得写事务；PostgreSQL 对批次及来源行加锁。同一批次的并发确认中，一个请求完成首次写入，其他请求锁后重读并返回幂等结果，因此数据库只保留一条确认审计。

## 5. 与订单退款的边界

订单任一明细进入供应商结算批次后，整单自动退款失败关闭。这一规则同时保护待确认和已确认批次，避免退款使批次失效或形成已确认结算与退款并存的冲突事实。

需要处理此类退款时，必须等待后续独立的结算撤销或冲销设计；当前服务不会删除结算明细、回退确认状态或自动修改成本。

## 6. 当前明确不做

- 不开放结算 HTTP API 或后台页面；
- 本服务本身不生成 Excel；M6-4 由独立报告服务只导出已确认批次；
- 不标记付款、转账或开票状态；
- 不撤销、删除或冲销结算批次；
- 不实现已进入结算订单的自动退款或人工异常恢复；
- 不改写积分、库存或现金返现数据。
