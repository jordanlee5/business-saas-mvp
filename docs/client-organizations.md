# 客户与分支机构及商城清单归属

2026-11-18完成三轮计划的第一轮：机构登记、上传授权、强制清单归属与不可覆盖的批次记录。用户确认总公司默认比例可由分支覆盖；各客户、分支积分独立；价格规则保存成功即生效。比例配置与商城计价、积分隔离属于后续两轮，本轮没有改变商品售价或积分扣减。

## 后台操作

1. 运营管理员或超级管理员进入“积分商城 → 客户与分支机构”，先登记总公司，再选总公司登记分支。填写统一机构编号、完整名称和归属地，不只用地名作为身份。
2. 为实际上传账号授权对应机构。一个机构可有多个账号，一个账号可获多个机构授权；后台权限与账号是否启用均会重新核验。
3. 上传方进入原“模板管理”对应的上传页面，只能看到获授权且启用的机构模板。下载后填写会员资料；模板已经带入机构编号、分支机构名称和分支归属地，新增会员行时复制这三列。
4. 每份清单只归属一个机构，不同分支分别上传。三项机构字段逐行必填，且须与登记及账号授权一致。任选一行缺填、机构混合、名称或地区不符，整份拒绝，不产生部分会员记录。
5. “上传记录”显示当时的机构名称、归属地与编号，历史商城清单没有归属时明确显示“待核实”。

例如哈尔滨分公司与广西分公司使用各自的机构模板；即使都属于同一总公司，系统也保存不同机构身份。总公司直接承接的名单可以明确授权总公司机构，不以空字段代替归属。

机构身份与上级关系创建后保留；本轮提供启停，不提供变更历史归属或删除入口。录入错误时停用并正确登记，避免重新解释旧账。总公司停用会阻止其分支新上传；账号撤销授权不会改写已有批次。

现金返现沿用原五列模板与银行卡校验。没有已核验归属的现金清单不能通过“纠正渠道”变成商城清单，应按对应机构模板重新上传；有归属的商城批次纠正到现金再改回商城时，仍重新检查原机构及上传账号授权。

## 数据与权限

- 新增结构0023_client_organizations，只有三张新增表：client_organizations、client_upload_scopes、client_batch_ownerships。旧业务表、已有清单及积分没有自动改写或机构猜测。
- 批次归属与会员业务记录、上传通知在同一事务写入。通过业务记录的批次可追溯机构，独立保存当时总公司及分支名称、编号、归属地。归属不是随着上传账号配置变化而重新计算。
- 机构与授权管理仅限启用的运营管理员和超级管理员，具有表单校验、版本冲突保护和操作记录。上传方不能改机构或授权自己，不能下载、提交未授权机构的模板。
- 机构信息在保存批次前再次校验，下载过模板不代表永久有效。新上传文件使用随机文件名，避免同名同秒覆盖旧文件。
- 历史待核实归属、积分账户按机构分开、会员资格与价格统一关联均留给后续完整接入；第一轮基础功能不能等同于已完成客户价格隔离。

## 本轮验证与发布边界

隔离虚拟检查覆盖机构创建、二级层次、过期版本、权限、真实Excel下载填写上传、跨机构拒绝、整批回滚、撤权、旧模板及渠道兼容。独立SQLite与PostgreSQL17验证0022升级0023不改旧记录、模型与迁移一致，空表可退回、有机构数据时拒绝丢弃降级。新建PG实例验证后已停止。

跨版本回退在删除0023的空表前，先检查目标路径上将被删除的表是否已有数据，防止SQLite逐步提交后留下不完整结构。有数据时在首次删除前拒绝回退，保留原结构与版本；回退命令须指定完整目标版本。此保护不代替上线前一致恢复点，也不授权用旧备份覆盖新业务。

浏览器检查两个真实HTTP页面渲染结果，在1440、768、390宽度均无页面横向溢出，无脚本错误；机构列表按需横向滚动。界面截图只含虚拟资料。具体计数、日志摘要与范围见[本轮证据](validation/client-organizations-20261118.json)。

全部在独立源码副本验证，现有8900验收、用户素材和恢复点没有修改，真实库未访问，未升级云端、接短信或提交微信审核。尚未生成包含本轮结构的新候选镜像，下一轮继续后台比例配置，之后完整接入价格和积分交易隔离再统一验收。沿用[长期原则](collaboration-principles.md)与[分层定价计划](customer-pricing-proposal.md)。
