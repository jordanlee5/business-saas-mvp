用户已确认采用名单核验与微信绑定，不做零知识证明。第一轮后台资格管理已实现：已承接商城名单确认、激活证据关联、独立启停及有效期、经办和变更留痕，详见[操作说明](member-qualification-admin.md)。真实库未迁移，旧会员不自动授予资格。第二轮服务端、商品图片和新兑换资格校验现已完成，详见[访问边界](member-catalog-access.md)。第三轮小程序入口、带身份图片下载和缓存清理已完成虚拟验证，资格入口界面已获用户确认；真实微信授权、鉴权下载与真机清理仍待环境就绪；当前服务端不再匿名开放目录及商品图片。

## 建议与现状

建议第一版采用“甲方授权名单 → 运营校验并确认 → 一次性领取凭据 → 微信身份绑定 → 每次请求校验会员浏览资格”。正常会员完成一次绑定后通过有效会话进入商城；名单外访客只看到服务范围说明、资格激活、隐私说明及公司客服入口，不获取商品目录、积分价格或商品图。

规划时 `app/api/miniprogram_v1.py` 的 `/categories`、`/products` 和商品详情无需会员登录；现已要求会员身份与有效资格，`/uploads/mall_products` 也已改为受保护路由。订单、积分、地址、物流则已验证本人身份。现有激活流程核验商城业务单、手机号、车牌和一次性码，并由服务端交换微信 code，不能只凭客户端提交的 OpenID 或手机号放行。不能把现有后台登录 Cookie 当作会员身份。

访问控制能减少无关访问和批量采集，不能证明来访者动机，也无法阻止获准会员截图或转发。服务范围按真实业务资格设置，不按是否投诉决定；客服、售后、权益申请与依法配合检查的途径保留。正常商品说明与经营记录仍需真实、可核查。

## 为什么第一版不采用零知识证明

[W3C 可验证凭证数据模型](https://www.w3.org/TR/vc-data-model/#zero-knowledge-proofs)描述了持有人通过零知识方式证明某项资格、减少披露其他属性的用途。它仍需要可信签发方、凭证发放、持有者绑定、有效期及撤销机制。其作用不是识别恶意投诉者，也不是替代权限校验。

当前名单本来就传入本公司的 SaaS，履约也需要联系及收货信息。现阶段增加证明电路、凭证钱包和撤销基础设施，不能消除这些已发生的数据处理。因此建议先落实最少资料、短期会话、资格撤销与审计，不引入新密码学库。一次性码、令牌、手机号摘要、普通签名或 Merkle 路径都不能直接称为“已经实现零知识证明”。

未来如果甲方要求“完整名单留在甲方，商城只验证资格、不获知具体名单身份”，才开展单独验证：甲方签发匿名资格凭证，会员持有密钥，商城验证资格证明及新鲜挑战、范围和有效期；补充撤销、防重放、设备丢失恢复、共享凭据风险与专家审查。即使如此，下单收货与售后身份仍需另外处理，不能承诺整个系统匿名或不可关联。

## 拟定的权限规则

浏览资格与积分余额分开。建议新增可审计的资格记录，关联甲方/业务来源、导入批次、内部会员、启停状态、有效期、经办人、时间和原因。只有审核通过且成功绑定的资格可用于浏览；客户端不能自行指定有效甲方或资格。

| 情况 | 商品浏览及新兑换 | 历史订单、物流、售后与权益申请 |
| --- | --- | --- |
| 未登录或名单外 | 仅入口说明与资格办理，不返回目录或图片 | 登录后仍须本人校验 |
| 名单内、未绑定 | 完成一次性核验后进入 | 不通过输入手机号直接查历史 |
| 已绑定、资格有效、积分为零 | 可以浏览；兑换按积分和库存决定 | 本人可查询 |
| 浏览资格到期或撤销 | 下一个请求即拒绝新的目录与兑换访问 | 本人仍可处理既有订单及申请 |
| 同时有多个甲方资格 | 任一有效资格满足对应范围即可；撤销一项不扩大其他项权限 | 不改变订单归属 |
| 账号被盗或全账号停用 | 单独的安全处理和恢复流程 | 提供人工核验及客服渠道 |

现有 `Member.is_active` 会影响全部会员接口，不能直接用它实现“只撤销商城浏览资格”。名单重复上传保持幂等；名单文件遗漏某人不能默认为撤销，需显式操作并留痕。禁止上传方查看其他甲方名单；批次预览、导入、启停和导出按运营角色授权。

拟定默认：已获准且有效的会员可以浏览全部当前商城商品，不自动按甲方拆分目录；零积分不撤销浏览。后续实施前复核这两项业务默认，以及有效期、旧会员承接与人工核验规则。非车辆类名单不强行收集车牌，按实际资格证据调整核验字段；不额外默认收集身份证照片。

## 分三小轮实现，每轮虚拟数据验证

1. **资格与后台管理**：复用已审核的商城业务来源，补资格记录、批次确认、启停及变更审计；一次性激活凭据只保存必要摘要，失败统一提示且限次，不暴露某个手机号是否在名单。用两家虚拟甲方、重复名单、名单外会员、有效/撤销/到期会员验证隔离与恢复。真实名单不导入测试环境。
2. **服务端完整闭合访问**：统一校验分类、搜索、分页、详情、规格、原图和本轮生成的缩略图；直接调用 API、猜链接、Range/HEAD 请求不能绕过。移除公开商品图片挂载，替换为可验证会员资格的文件入口，后台预览另外验证运营权限。原始静态 URL 和网关目录都要关闭，不能只改小程序页面。旧缓存、对象存储或 CDN 副本需要清理并核对，已经下载的图片无法远程收回。会员目录及受保护图片禁止共享缓存；跨进程撤销从数据库生效，不能只依赖单进程缓存。
3. **小程序入口与验收**：首次打开进入资格说明，用户主动同意所需隐私处理后核验并绑定；过期、撤销、无资格分别给出可操作提示。图片优先评估带会话鉴权下载为临时本地文件，再渲染，需补微信真实环境兼容、下载域名、并发与临时文件清理验证；若改用短时链接，须明确它在有效期内可被转发，不能描述成仅本人可用。退出与资格失效时清理页面、购物车中的商品展示缓存和临时图片，切换账号不得显示上一个会员内容。历史订单及权益入口保留。

遵循[OWASP 权限校验建议](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：服务端默认拒绝、逐请求验证，包含文件资源。数据库或资格查询异常时返回可重试提示，不降级开放目录。三轮闭环并通过后才能对外称为“仅名单内会员可浏览”；只有第一轮资格表或前端拦截不能算完成。

验收至少包含：名单内首次绑定与再次登录；名单外/伪造身份/过期及撤销令牌；跨甲方与跨会员；复制详情和图片链接；图片缓存及账号切换；跨进程撤销；故障恢复；撤销前已提交订单的后续查询；零积分会员；管理员越权与日志不泄露凭据；有效会员兑换、幂等重试和库存保持正常。

## 与部署准备的关系

不需要因这一方案更换服务器或增加区块链节点。当前 CVM 测试采购候选与[购买指南](test-server-purchase.md)保留，主体确认后再继续。若正式产品决定只向名单内开放，则以上访问闭环应列为正式对外开放前的条件；可以先在受限测试环境用虚拟名单验收。平台申报时如实说明服务范围和测试流程，提供受控的有效测试身份，不设计识别审核人员或隐藏功能的特殊通道；当前仍不提交微信审核。
