## 会检查什么

运行 `python3 -m tools.staging_monitor`，一次输出一份 JSON 检查报告：

| 检查 | 正常要求 | 异常提示 |
| --- | --- | --- |
| 应用、数据库、OCR | 每个服务恰有一个项目所属容器，正在运行且健康检查为 healthy | 缺失、重复、停止、启动中、不健康或检查失败 |
| 指定磁盘 | 可用空间同时不少于 5GiB 和 10%（可调整） | disk_low；路径不可读时检查失败 |
| 指定备份 | 文件清单及摘要匹配，属于当前项目，完成时间不超过 36 小时 | 缺失/损坏、来源不符、过期或时间无效 |

返回码 0 表示本次检查正常，1 表示发现问题，2 表示参数配置错误。恢复服务或更换为完整的新备份后再次运行，正常结果即可作为恢复记录。工具只读，不重启容器、不清理磁盘、不创建备份、不改数据库，也不自动发送外部消息。每次保留报告时间与结果，运维系统可据返回码触发告警。

Docker 每次调用有 10 秒超时，失败不会打印原始错误或日志，其他检查继续。仅读取容器标签、运行状态、健康状态，报告不包含环境变量、密码、令牌、私钥、备份内容或主机路径。Docker 不可用或权限不足会报警，不能当作正常。

## 服务器就绪后由开发方配置

在仓库目录执行，例如：

```sh
python3 -m tools.staging_monitor \
  --project saas-pg-test-first \
  --disk-path /var/lib/docker \
  --disk-path /srv/saas-backups \
  --backup /srv/saas-backups/test-latest-complete
```

路径必须改为实际 Docker 数据目录和备份目录。`--disk-path` 可以重复，需覆盖业务卷、数据库卷及备份实际所在文件系统；工具不会猜测或自动发现存储位置。`--backup` 必须指向已完成的具体备份目录，不指向符号链接。报告的 disk_1、disk_2 对应参数顺序。

部署账号需具备 Docker 只读查询所需权限和备份读取权限；Docker 套接字本身权限很高，只授权给受信任运维账号，不暴露给网页或会员。报告保存到仓库外运维目录。服务器开通后，开发方再安排周期检查、日志轮转、避免校验重叠，以及实际通知接收人/渠道；当前没有安装定时任务或发送告警。

新备份清单增加 UTC `completed_at`。原备份仍可按既有恢复工具校验和恢复；巡检对没有完成时间的旧备份报告 `backup_time_missing`，需重新做一份备份，不用目录修改时间冒充备份时间。时间超过当前时刻 5 分钟也报警。文件摘要校验改为每次读取 1MiB，减少大文件校验时的内存峰值；校验仍会产生磁盘读取负载，检查间隔应按实际备份大小设置。时间、来源、摘要清单是运维一致性记录，不能抵抗拥有备份写权限的人同时篡改文件与清单。

## 验证与边界

14 项专项及备份安全兼容检查通过。真实隔离 Docker 容器完成 10 个检查点：正常、数据库容器停止/恢复、OCR 不健康/恢复、虚拟备份损坏/修复、过期/更新及只读复查。磁盘低余量、Docker 超时、错误项目、缺失/重复容器、时间边界及退出码使用可控夹具验证；没有填满真实磁盘。

这次容器运行合成健康检查，备份是合成文件，不是新增 PostgreSQL 恢复或业务交易演练。既有备份恢复证据见 [PostgreSQL 部署说明](postgres-staging.md)。巡检沿用服务原有健康检查；`/health` 正常不代表所有业务交易成功，`pg_isready` 也不证明所有 SQL 正常。HTTPS、证书到期、外网可达性、异机备份、真实恢复及通知送达仍需目标服务器验证。不能据本机巡检通过宣称公网部署已验收。
