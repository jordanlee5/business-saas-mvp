# OCR 识别隔离与故障保护

2026-11-05，从 `c16b08c` 接续。使用虚拟图片、会员与独立 PostgreSQL，真实业务库未写入、未升级；未提交微信审核，未购买或部署公网服务器。

## 操作变化

后台仍通过“上传并识别”取得本次结果。每次最多 20 张、每张最多 8MB；已成功识别的重复图片沿用原有去重与匹配规则。失败文件记录在上传批次中，可只重传失败的图片。识别服务繁忙、超时或停止时显示明确原因，不显示内部服务地址或识别程序的错误详情。

本轮保留上传页面等待结果的方式，**不提供持久任务队列或关闭页面后的进度查询**。同时有多位运营提交时，独立识别服务最多接受一个正在处理的图片请求，其余立即返回繁忙；不建立无界等待队列，也不暗中切回网页进程识别。未来需要批量自动排队时，应另做任务持久化、重试和进度界面。

## 实现与资源边界

- PostgreSQL 部署包默认 `STAGING_OCR_MODE=isolated`。应用 2 CPU / 4GiB，数据库 1 CPU / 1GiB，OCR 1 CPU / 1GiB；合计 4 CPU、6GiB 容器内存上限。为 4 核 8GB 候选测试服务器保留系统余量，实际机器仍需复测。
- 网页应用不在导入时加载识别模型。等待识别前归还数据库连接，会员读取和兑换不必等待该上传持有的连接。
- OCR 服务使用独立内部网络，没有主机端口，不挂载业务数据卷，不持有数据库密码和会员签名密钥。文件系统只读，临时目录 128MiB，进程数上限 64，使用非 root 用户并去掉额外能力。
- 每张图片在可终止的独立子进程内识别，原生计算线程限制为 1；识别总时限 30 秒，包括模型加载。超时终止并回收子进程，临时图片和裁剪文件随本次任务清理。
- 只接受 PNG/JPEG、最多 1,600 万像素。上传到识别服务的请求体最多 8MB，接收超时 10 秒；客户端使用固定内部地址、连接超时 3 秒、读取超时 40 秒，不使用系统代理或自动跟随跳转。
- 模型随现有镜像构建过程准备，OCR 内部网络不提供外网访问。识别子进程不导入业务数据库模块，只返回文字，不自行创建凭证或审核记录。数据库、匹配及权限判断仍由原应用执行。
- OCR 没有新的持久业务状态，因此不新增表结构；现有备份仍包含数据库、原始凭证及业务附件。临时识别文件不需要恢复。服务恢复后可重传失败文件；不会自动重放停机前请求。
- 原本的本机开发入口默认 `OCR_EXECUTION_MODE=inline`，保持兼容。实际服务器用 PostgreSQL Compose 的隔离配置；配置为 isolated 后出现错误不会回退为 inline。

上传张数和大小检查发生在应用收到表单之后，不能替代公网入口对请求大小、连接数和慢上传的限制；本轮没有宣称完成互联网恶意流量防护。

## 开发方部署与检查

从仓库根目录按 [PostgreSQL 部署说明](postgres-staging.md)初始化全新虚拟环境。构建应用镜像后，应用和识别服务使用同一明确镜像；Compose 启动应用时会先等待数据库及 OCR 健康检查。OCR 后续故障不停止已经运行的应用。

```sh
docker compose -p saas-pg-test-first -f deploy/staging-postgres/compose.yaml build app
docker compose -p saas-pg-test-first -f deploy/staging-postgres/compose.yaml up -d --wait app
docker compose -p saas-pg-test-first -f deploy/staging-postgres/compose.yaml ps
```

排查 OCR 时由开发方查看独立服务状态，必要时只重启它；不为处理识别故障重启数据库。不要公开 8001 端口，不要给 OCR 服务挂载业务卷或数据库秘密资料。健康检查表示服务可以接受连接，具体模型是否可识别仍需用虚拟图片验证。

## 验证方法

`test_ocr_isolation.py` 覆盖限流、健康检查、超时子进程真实终止、临时文件清理、异常响应、失败时禁止本地回退、无凭据与无权限拒绝、等待识别期间数据库连接已释放、重复上传及失败后重传。

真实容器对照仍使用 400 商品 / 4,000 SKU、100 个持续浏览任务，混入图片下载、后台维护、真实 OCR、24 次领取和 24 人争兑 12 件商品。每档两轮：30 秒浏览 + 60 秒混合操作。测试端独立容器占用 2 CPU / 1GiB，未计入服务端预算。

对照均使用同一版代码与镜像：
- inline：应用内识别，应用 3 CPU、数据库 1 CPU；独立 OCR 容器在计时前停止。
- isolated：应用 2 CPU、数据库 1 CPU、OCR 1 CPU；识别单线程与独立服务同时生效。

所以结果反映的是整套隔离配置的效果，不能将改善全部归因于进程拆分。应用内模型在首次使用时加载；两档均包含冷启动成本，后续热态另需长期测试。每档订单、积分和全部 SKU 库存逐项核对，不用重试抹掉服务错误。

故障演练额外停止 OCR 服务，验证后台失败提示、失败批次记录、会员浏览/积分读取/下单/取消和他人订单拒绝；恢复后重传一次成功，再传同图不会增加凭证。并直接验证独立服务两个同时请求返回一个成功、一个繁忙，异常图片被拒绝。

## 本轮结果（两轮分别保留）

完整 Linux 回归运行 **867 项，858 项通过、9 项因 PostgreSQL 环境条件跳过**，耗时 334.241 秒。新增 OCR 检查 16 项全部通过。独立容器对照另实际使用 PostgreSQL 16，不将跳过项计为通过。

两档计时阶段均无非预期 HTTP 或网络失败。每档 72 个账户和 72 笔领取、24 笔全部取消的订单，4,000 条库存与全部会员积分对账一致；4 份 OCR 均得到文字，没有超卖或重复预占。预期库存冲突 409、跨会员查询 404 都按业务拒绝核对，不计系统故障。

停机恢复演练通过：停止 OCR 后后台记录一次识别失败，会员仍可浏览、读积分、创建并取消订单；其他会员查看该订单返回 404。恢复后重传成功，再传同图记为重复。故障演练结束共 25 笔取消订单、5 张凭证、1 次失败与 1 次重复上传，库存预占为零、账户恢复 100 积分。独立 OCR 无公网端口、无业务卷及数据库秘密，真实并发请求一个成功、一个繁忙，坏图返回 422。

## 复验命令

只在 Linux Docker 的隔离测试宿主运行。所有数据库、文件和秘密均由随机专用项目生成，不接收外部数据库 URL；测试结束清理自己的容器与卷。输出目录必须不存在。

```sh
docker build -t business-saas-ocr-review:local .
python3 -m tools.rehearse_mixed_workers --image business-saas-ocr-review:local --seconds 60 --workers 1 --server-cpus 4 --ocr-mode inline --output /tmp/ocr-inline
python3 -m tools.rehearse_mixed_workers --image business-saas-ocr-review:local --seconds 60 --workers 1 --server-cpus 4 --ocr-mode isolated --verify-ocr-failures --output /tmp/ocr-isolated
```

不要并行运行两档或同时运行完整回归，以免污染时延对照。WSL2、本机 Docker 网络和两轮短测不能代表公网云主机、真实微信服务或长时间活动容量。
