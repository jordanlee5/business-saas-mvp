# 小程序下单、收货快照与会员订单（2026-10-28，本机真实库已升级）

购物车“确认兑换”进入确认页，重新读取商品与地址，展示积分合计和包邮规则。会员明确选择地址后提交，后台接收订单并原子预占积分和库存。会员可在“我的订单”查看列表、详情及物流，并取消待处理订单。后台沿用既有确认履约、发货、完成、整单退款和供应商结算状态规则，订单详情新增下单时收货快照。

## 接口与事务

所有接口位于 `/api/miniprogram/v1/orders`，使用现有会员 Bearer 会话及 `Cache-Control: no-store, private`。

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| POST | 空路径 | 新订单201；相同请求重放200 |
| GET | `?page=1` | 当前会员分页订单摘要，每页20条 |
| GET | `/request/{request_id}` | 当前会员查询不确定提交结果 |
| GET | `/{order_public_id}` | 当前会员订单明细、收货快照及物流 |
| POST | `/{order_public_id}/cancel` | 复用既有CREATED取消/资源释放及精确重放规则 |

请求包含32位十六进制请求号、地址公开编号、六个预期地址字段，以及最多20种不重复商品规格（每种1–99件、预期单位积分价）。身份只能来自会话，不接受会员ID。服务端重新读取目录并比较预期价格与地址；变化时拒绝，不静默按新内容下单。响应不包含人民币成本、供应商资料、内部ID或积分批次分配。

SQLite写入先取得BEGIN IMMEDIATE；PostgreSQL锁会员行，使用现有订单服务固化商品价格、FEFO积分分配和库存预占。订单、快照、积分和库存为同一事务，快照失败也整体回滚。请求号按会员隔离，规范化请求摘要包括商品、数量、价格和所选地址；相同请求返回原单，不同内容冲突。重放先查原单，不依赖当前地址簿仍有原记录。

## 快照与兼容

迁移 `0012_member_addresses → 0013_order_delivery_snapshot` 只增加空表 `order_delivery_snapshots`，通过订单ID关联；不关联可删除的地址簿行。地址编辑或删除不改变订单收货信息。历史订单不伪造快照，前后端均明确显示“历史订单未保存收货快照”。快照非空时禁止自动降级。

启动就绪检查要求0013及快照字段。2026-10-28本机已在用户确认后完成0012→0013真实库升级、执行时备份和运行态检查。其他仍为0012的环境不能启用新后端，须先完成各自备份、隔离演练并取得升级确认。演练工具：`python -m app.order_delivery_migration_check --source <真实SQLite路径> --output <全新私有目录>`；该工具无真实升级模式。原0011→0012历史演练仍单独验证当时表结构和数据，不将历史目标冒充当前启动就绪状态。

## 客户端恢复与隐私

写入中阻止重复点击；页面隐藏清空展示的地址，返回时等待在途写请求再读取。网络中断、会话变化、无效成功响应时保留本次提交标记，先查询原结果，或沿用同一请求重试。小程序重启后可重新核对同一次兑换，仍沿用原请求号，不能通过刷新生成第二单。若原单已存在而重新核对内容不同，应查询原单查看结果。

持久存储仅包含会员公开编号、请求号及公开购物车行，不保存姓名、电话、详细地址、完整下单报文或令牌。完整重试报文仅在进程内存保留，并按会员隔离。确认订单成功后清理标记；仅移除仍与提交数量一致的购物车行，保护途中发生的购物车修改。

## 验证边界

新增SQLite及PostgreSQL HTTP测试覆盖快照不随地址变化、精确幂等、跨会员隔离、输入隐私、价格变化、库存/积分不足、快照失败整体回滚、并发同请求、取消释放和后台履约至退款的查询一致性。客户端模拟检查覆盖恢复、会员隔离、重复点击、页面切换和取消确认。

自动化不代表真实微信平台验收。正式AppID仍未写入配置，隐私审核通过标志仍为空；原六项DEFERRED继续保留。没有提交推送、发布或向真实业务库填充测试会员/商品/订单。
