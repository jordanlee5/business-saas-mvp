# 积分调整服务说明（M3-4）

本轮从 `bf865bb` 建立后台人工积分纠错领域服务，沿用 `0003_member_activation_security`，无需数据库迁移。当前没有新增命令行、后台页面或 API；请勿为测试或日常操作编写 `python -c` 脚本直接连接真实数据库。

## 适用边界

人工调整用于纠正既有积分批次的记账差错，不是发放奖励、订单消费、退款或延期工具。

| 场景 | 处理规则 |
| --- | --- |
| 正向调整 | 只增加批次可用积分，且调整后“可用 + 预占”不得超过该批次原始授予积分 |
| 负向调整 | 只减少批次可用积分，不得扣成负数 |
| 预占积分 | 不修改；本轮不提前实现订单释放或消费 |
| 已用尽批次 | 可在未到期且未冻结时正向恢复，状态转回 `ACTIVE` |
| 余额清零 | 无预占余额时状态转为 `EXHAUSTED` |
| 已到期或冻结 | 拒绝调整；到达 `expires_at` 的精确时刻即视为已到期 |
| 来源业务 | 不修改领取状态、业务金额、渠道或上传批次 |
| 原始权益 | 不修改 `granted_points`、`expires_at` 或激活时间 |

积分统一按两位小数处理。任何账户或同账户批次的缓存余额与不可变流水不一致时，服务失败关闭，不会以人工调整掩盖漂移。

## 权限、审计与幂等

- 仅数据库中仍为启用状态、管理员级别为 `super_admin` 的账号可执行；服务重新读取操作者，不信任调用方传入的角色文字。
- 原因和请求号必填。原因规范化空白后最多 500 个字符；外部请求号最多 82 个字符，流水内统一保存为 `points-adjustment:<请求号>`。
- 成功请求新增一条 `mall_points_adjust` 管理员操作日志和一条非零 `ADJUST` 流水。流水记录操作者、原因和变化值，并通过 `ADMIN_ACTION_LOG` 来源反向关联日志。
- 完全相同的请求号、批次、变化值、操作者和原因可安全重放，不重复生成记录、修改余额或增加账户版本。
- 相同请求号携带不同内容、引用非调整流水，或原审计日志缺失/被修改时，服务拒绝继续。

日志、流水、批次余额与状态、账户余额与版本在同一事务写入。写入后的一致性复核失败时必须整体回滚。

## 代码接入约束

低层函数 `adjust_points_grant` 只执行校验、加锁、写入和 `flush`，不自行提交；已有上层事务可以调用它，但异常时必须回滚整个事务。独立后台操作应使用 `execute_points_adjustment(engine, ...)`，它在 SQLite 上先执行 `BEGIN IMMEDIATE`，并负责成功提交或异常回滚。

未来后台页面接入时必须同时满足：

1. `actor_admin_id` 只能来自已认证的服务端管理员会话，禁止从表单、查询参数或 JSON 请求体接受可替换的管理员编号。
2. 页面再次使用现有商城细权限做入口拦截，领域服务的权限校验仍须保留，形成双层保护。
3. 请求号由服务端为一次提交生成并随确认表单固定，浏览器重试复用同一编号；不同操作不得复用。
4. 页面明确展示目标会员、积分批次、原始授予额、可用/预占余额、到期时间和调整后余额，并要求填写具体原因和二次确认。
5. HTTP 成功响应只能在数据库事务提交后返回；数据库完整性异常不得改为直接更新缓存余额的“补救”路径。

当前没有可供管理员操作的入口，因此页面冒烟只能证明既有系统未受影响，不能视为一次真实积分调整验收。后续接入会员详情与 Excel 导出时，再增加页面权限、CSRF、敏感信息最小展示和导出审计测试。

## 测试与数据库范围

专项测试覆盖正负调整、两位小数、授予上限、预占隔离、已用尽恢复、到期与冻结、权限、幂等冲突、审计关联、余额漂移、事务回滚、旧会话刷新及 SQLite 并发。运行：

```powershell
python -m unittest -v test_points_adjustment_service.py
```

默认测试中的 SQLite 并发用例证明本机写入口能够串行化，但不替代 PostgreSQL 验收。启用 PostgreSQL 前，仍须在名称以 `_test` 结尾的独立可清空测试库验证行锁、唯一键冲突、UTC+8 时间和提交/回滚行为，严禁使用开发共享库或生产库。
