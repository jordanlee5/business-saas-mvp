# M5-5 订单发货与完成生命周期

## 范围

M5-5 在 M5-4 确认履约及积分消费、库存出库证据之上，提供内部 `FULFILLING → SHIPPED → COMPLETED` 领域服务。第一版物流由运营人员手工录入物流公司和运单号，不依赖付费物流查询 API。

本切片仍只提供领域服务，不增加 HTTP 路由、会员端页面或管理员订单页面。

## 发货

`execute_order_shipping()` 只允许启用中的超级管理员和运营管理员操作证据完整的 `FULFILLING` 订单。物流公司与运单号均为必填且最长 100 个字符；同一物流公司下的运单号不能用于多张订单。发货时间不能早于原确认履约日志时间。

首次发货在同一事务写入订单状态、物流公司、运单号、发货时间和唯一 `mall_order_ship` 管理员日志。已处于 `SHIPPED` 的订单只接受物流公司与运单号完全相同的精确重放；参数改变、证据缺失或已有完成证据时失败关闭。

## 确认完成

`execute_order_completion()` 只允许相同两类启用管理员把证据完整的 `SHIPPED` 订单推进到 `COMPLETED`。完成时间不能早于发货时间，首次操作同事务写入状态、完成时间和唯一 `mall_order_complete` 日志。已完成且证据完整的订单可安全重放，不修改首次时间、操作人或日志。

`COMPLETED` 只表示本订单的履约生命周期已闭合。供应商结算尚未实现，不会因状态改为 `COMPLETED` 自动生成结算记录或支付任务。

## 证据与原子性

发货及完成前都会重算订单积分、成本、数量和积分批次分配合计，并验证唯一确认履约日志、每个积分批次的 `CONSUME` 及每个 SKU 的 `OUTBOUND` 证据。完成还会验证发货日志内容、操作人及时间与订单字段一致。

缺失、重复、冲突、被篡改或时间倒置的证据都会阻止状态推进，服务不会自动修复或补写。`execute_*` 入口使用独立事务：SQLite 采用 `BEGIN IMMEDIATE`，PostgreSQL 采用行锁；首次变更与日志一起提交或一起回滚。

## 数据库迁移

`0009_order_shipping_completion` 在 `orders` 新增 `shipping_carrier`、`tracking_number`、`shipped_at` 和 `completed_at`，并增加完整性检查、状态检查、物流公司与运单号组合唯一约束及时间/运单号索引。必需应用表仍为 26 张。

因为 `0008` 没有物流证据字段，如果源库已存在 `SHIPPED` 或 `COMPLETED` 订单，迁移不会猜测或伪造物流证据，而是拒绝升级并要求先人工审计。存在发货/完成状态或任何对应字段时，降级也会被拒绝，防止证据丢失。

SQLite 真实库升级前必须停止应用，先运行 `python -m app.migration_upgrade_rehearsal` 在独立副本上验证 `0008 → 0009`，再保留真实库及 `uploads/` 备份后单独批准升级。

## 明确不实现

本切片不实现物流轨迹查询、多包裹、拆单发货、订单 API 或页面、退款、退库、售后异常恢复、供应商结算或真实测试数据。后续 M5-6 已在完整完成证据上实现内部整单退款，见 [订单原子退款说明](order-refund.md)。

## 验证

专项测试覆盖正常发货与完成、精确重放、并发操作、物流参数冲突、权限、状态、时间顺序、原履约证据篡改、物流审计篡改、升降级安全和结构约束。独立 PostgreSQL 集成验收会连续执行并发确认履约、发货和完成，并确认每阶段只有一套证据且测试库最终清理。
