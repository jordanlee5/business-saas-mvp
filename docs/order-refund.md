# M5-6 已完成订单原子退款与双资源恢复

## 范围

M5-6 在 M5-5 完整履约证据之上提供内部 `COMPLETED → REFUNDED` 整单退款领域服务。首次退款在一个事务内恢复原消费积分、退回 SKU 库存、写入退款事实及管理员审计；不允许只修改订单文字状态。

本切片仍只提供领域服务，不增加 HTTP 路由、会员端页面或管理员订单页面。第一版只支持整单退款，不支持部分商品、部分数量或部分积分退款。

## 准入与状态

`execute_order_refund()` 只允许启用中的超级管理员和运营管理员处理证据完整的 `COMPLETED` 订单。退款原因必填且最长 500 个字符，退款时间不得早于订单完成时间。

服务在写入前重算订单积分、成本、数量和积分批次分配合计，并验证唯一的确认履约、发货及完成审计，每个积分批次的 `RESERVE → CONSUME` 和每个 SKU 的 `RESERVE → OUTBOUND` 链路。任一状态、合计、操作者、时间或证据异常时失败关闭且整体回滚。

## 积分恢复

积分严格按订单保存的实际分配退回原积分批次，每个批次追加唯一 `REFUND` 流水，不修改既有 `RESERVE` 或 `CONSUME`。退款同步增加批次与账户可用积分、账户版本，并在提交前按不可变流水重新核对缓存余额。

若任一原积分批次在退款时已经到期或状态不允许自动恢复，整单退款失败关闭，进入后续人工处理；服务不延长原到期时间、不新建临时批次，也不把到期积分转入其他批次。冻结批次保持冻结，其余合法批次恢复为 `ACTIVE`。

## 库存恢复

库存按订单项 SKU 和原 `OUTBOUND` 证据追加唯一 `RETURN` 流水，增加现存数量但不改变预占数量。每次退回前后均按完整库存流水核对余额和版本；不允许退回其他订单、其他 SKU、错误数量或缺少出库证据的库存。

## 幂等、并发与审计

首次退款同时写入订单 `REFUNDED` 状态、退款原因、退款时间、积分 `REFUND`、库存 `RETURN` 和唯一 `mall_order_refund` 管理员日志。相同原因的精确重放返回首次结果，不修改首次时间、操作者、流水或日志；不同原因重放失败关闭。

SQLite 独立执行入口使用 `BEGIN IMMEDIATE`，PostgreSQL 使用事务与行锁。并发相同请求只允许一方首次写入，另一方必须读取并验证同一套完整证据后返回重放结果。

## 数据库迁移

`0010_order_refund_recovery` 在 `orders` 新增 `refund_reason` 和 `refunded_at`，并扩展物流、完成及退款状态约束；必需应用表仍为 26 张。

因为 `0009` 没有退款证据字段，如果源库已存在 `REFUNDED` 订单，迁移不会猜测积分和库存恢复事实，而是拒绝升级并要求人工审计。存在退款状态或证据时，降级到 `0009` 也会被拒绝，防止丢失事实字段。

SQLite 真实库升级前必须停止应用，先运行 `python -m app.migration_upgrade_rehearsal` 在独立副本上验证 `0009 → 0010`，再保留真实数据库及 `uploads/` 独立备份后单独批准升级。

## 明确不实现

本切片不实现订单 API 或页面、部分退款、换货、退款后再次履约、已到期积分的自动补偿、人工异常恢复、供应商结算冲销或真实测试数据。

## 验证

专项测试覆盖正常整单退款、原批次积分恢复、SKU 库存退回、精确重放、并发操作、权限、状态、原因与时间边界、原批次到期、消费证据篡改、升降级安全和数据库结构约束。独立 PostgreSQL 集成验收会连续执行并发确认履约、发货、完成和退款，并确认每阶段只有一套证据且测试库最终清理。
