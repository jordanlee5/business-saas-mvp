# 单进程、多进程混合压测与采购判断

2026-11-05，从 `35b6aa4` 接续。仅虚拟数据、独立 PostgreSQL 16 和临时 Docker 项目。真实业务库保持原文件哈希和结构版本；没有购买服务器、部署公网或提交微信审核。

## 本轮结论

可以进入测试服务器购买与公网联调阶段。建议先用 **CVM 4 核 8GB** 做测试，保留升配选择；还不能据此承诺正式活动的 100 人同时兑换体验。4,000 个 SKU 本身没有形成容量障碍；并发时的 CPU、数据库锁等待和图片出口更值得关注。

两个进程在相同 4 CPU 总配额下提高纯浏览吞吐，但叠加领取、兑换和 OCR 后尾部响应变慢。增加到 8 CPU 总配额后，双进程集中兑换明显改善，仍存在数秒等待。内存没有出现耗尽，**本轮没有验证 16GB 内存的收益**。默认生产进程数仍为 1，没有自动改成双进程。[购买与配合步骤](test-server-purchase.md)

## 场景和测量方法

- 400 件商品，每件 10 个 SKU，共 4,000 个 SKU；每个 SKU 都有对应库存余额和入库流水。目标争兑规格为 12 件，其余规格按 10、20、30、40 件分布。
- 400 个公开商品图片路径，内容为同一张生成的 768×768 JPEG，每张 327,009 字节。下载完整图片并核对摘要，没有用空响应代替下载。
- 每组使用全新库，预置 24 个虚拟会员、120 份虚拟业务领取凭据。每轮增加 24 次并行领取，并保留正常 600,000 次凭据派生成本。微信换取身份为合成响应，不调用真实微信服务。
- 每组重复两轮：先 30 秒纯商品列表浏览，再 60 秒混合操作。始终有 100 个无思考间隔的浏览任务；混合浏览按 3 次列表、1 次详情、1 次完整图片下载循环。
- 混合阶段同时运行后台目录查询及分类维护、两份串行真实 OCR 图片上传；第 2 秒开始 24 次领取，第 5 秒开始 24 人争兑 12 件库存。成功订单重复提交两次、跨会员查看、重复取消两次。
- 成功兑换必须恰好 12 笔，其余 12 次为库存冲突 409；跨会员查看必须为 404。这些预期业务拒绝不计服务故障。异常响应立即失败，压测端不以重试掩盖故障。
- 统计端到端 HTTP 时长，P95 表示约 95% 的该类请求在该时长以内完成。阶段尾部会等待已发出的任务完成，实际混合时长约 60～62 秒；报告保留真实持续时间。100 个持续发请求任务不等同于 100 个真人在线。
- 测试端位于独立容器，配额为 2 CPU / 1GiB，不占下面应用与数据库配额。每秒左右采样资源，每 5 次采样读取 PostgreSQL 连接和锁等待。三个配置顺序执行，期间没有并行跑回归测试。

| 对照组 | 应用配额 | 数据库配额 | 应用实际进程数 |
| --- | --- | --- | ---: |
| 4 CPU 单进程 | 3 CPU / 4GiB | 1 CPU / 1GiB | 1 |
| 4 CPU 双进程 | 3 CPU / 4GiB | 1 CPU / 1GiB | 2 |
| 8 CPU 双进程 | 6 CPU / 4GiB | 2 CPU / 1GiB | 2 |

宿主为本机 WSL2，20 个可见逻辑 CPU、约 7.65GiB 实际内存。配额不是独占物理核心；不是三台真实云服务器，也不是 8GB 与 16GB 内存的对照。三组使用相同应用镜像 `sha256:f8fded0434c4bcbe83b5dbd274ab08ca7cfa0d7ec1dc41b3d2977bf952160b39`。

短采样 CPU 峰值略高于配额源于采样窗口，不代表获得额外持续配额。连接数随进程数上升，扩进程时要同时核对数据库总连接预算。锁等待包括争兑同一库存的正常串行保护，不能为提速移除。PostgreSQL 的事务 rollback 统计也包括只读请求结束时的正常清理，不等于业务失败。

三组最终各有 72 个会员账户及 72 笔领取、24 笔全部取消的订单、24 次库存预占和 24 次释放。4,000 条库存及全部会员积分逐项对账通过，库存恢复种子值，没有超卖或重复预占；四份 OCR 均有识别内容，后台分类维护分别新增 29 / 29 / 30 行，退出后的保护页拒绝继续访问。

## 压测中发现并修复的问题

原版本在真实 HTTP 并发下出现 SQLAlchemy 连接池等待 30 秒后失败。当端点已经准备好响应、连接尚未归还时，响应校验还需要共享线程；另一些线程却正在等待连接，造成连接不能及时释放。私有会员接口的依赖还会在实际处理端点之前占用连接，混合兑换阶段再次暴露相同问题。

本轮修改会话生命周期：

1. 公开目录和相关会员读取/登录端点在返回已物化数据之后、响应序列化之前关闭本次请求拥有的 Session。
2. 会员地址、订单和权益申请将连接获取、处理和释放放到同一次工作线程执行中，避免持有连接等待端点线程。
3. SQLite 写操作仍在鉴权读之前取得原有写事务；显式传入的调用方 Session 仍由调用方负责。未扩大连接池、未减少安全校验、未变更业务表结构。

针对性回归使用只有 2 个连接、无额外溢出、1 秒等待上限的虚拟库，发起 50 次目录和 30 次无凭据地址请求，同时验证异常返回前连接已归还。相同两项用例在旧代码失败，在新代码通过。

完整 Linux 回归共运行 **851 项，9 项因 PostgreSQL 环境条件跳过，其余通过**，耗时 341.023 秒。不能将跳过项记为通过；本轮三组独立混合演练另外实际覆盖 PostgreSQL 16 的并发业务正确性。上一轮 66 项独立 PostgreSQL 检查没有在本轮重复运行，不计入本轮结果。

初期种子/测试端初始化失败、旧代码连接池超时、仅修复公开端点后的兑换失败，以及一次客户端连接中断均在本机保留。客户端将空闲连接保留时间降为 2 秒，低于服务端默认 5 秒，退出时收拢任务；最终完整三组均通过。失败尝试没有计入成功容量统计，不能声称所有开发过程中的请求都成功。

## 下一步和采购边界

1. **可以买测试服务器。** 用标准 CVM 4 核 8GB 起步，实际报价在约 1,000 元/月总预算以内。当前没有内存不足证据，先不因 4,000 个 SKU 自动购买 16GB。8 CPU 对集中兑换有收益，但正式升配要用目标机器复验，不能承诺线性翻倍提速。
2. **高峰与 OCR 分开安排，并继续开发任务隔离。** 当前 OCR 仍占用同一应用 CPU；后续可增加独立任务执行和进度查询，并对领取/兑换高峰进行有边界的容量管理。单纯增加 worker 无法保证混合场景更快。
3. **商品图公网带宽另测。** 本轮图片在 Docker 网络中传输，没有 10Mbps 出口限制。320KB × 100 张约 32MB，通过 10Mbps 出口理论就约 26 秒。后续优先图片压缩及缩略图，再按实际流量考虑公开图片存储和加速。
4. **补持续测试及公网验收。** 当前只有两轮短测，没有小时级稳定性、真实微信延迟、互联网 HTTPS、慢客户端或多运营人员同时 OCR 的容量结论。购机后用虚拟库补这些验证和异机备份恢复，再决定正式活动容量。真实库迁移与微信审核仍单独安排。

## 复验和证据

仅在 Linux Docker 的隔离开发/测试宿主运行，构建当前代码镜像；不要将它作为生产应用入口。脚本创建随机专用项目、私有秘密目录和全新数据卷，不接收真实业务数据库地址，不发布主机端口，结束后清理自己的容器和卷。

```sh
docker build -t business-saas-mixed-review:local .
python3 -m tools.rehearse_mixed_workers --image business-saas-mixed-review:local --seconds 60 --workers 1,2 --server-cpus 4 --output /tmp/mixed-four-cpu
python3 -m tools.rehearse_mixed_workers --image business-saas-mixed-review:local --seconds 60 --workers 2 --server-cpus 8 --output /tmp/mixed-eight-cpu
```

输出目录必须不存在，复测使用新的目录名。默认使用 Docker Compose 插件；需要独立 Compose 可按已有部署工具设置 `STAGING_COMPOSE_BIN`。测试专用微信替身入口要求显式虚拟 Docker 环境标识，正常应用入口不会启用。
