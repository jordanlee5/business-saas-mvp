## 本轮开发

`tools.staging_recovery_catalog` 新增可重复的 `--point` 参数，将已封存的手动恢复目录纳入原检查流程。可以只提供手动点，也可以与管理备份根混用；拒绝重复、别名重叠、链接、项目不符和损坏。手动点在镜像校验前后各做一次完整文件清单/摘要核验，不创建锁文件；中途变动会阻断。它不适用于仍在写入的目录，管理目录继续使用原生系统现有锁。

输出只用 `point_1` 等编号，历史恢复点缺镜像时即使候选镜像完整，也保留全部归档。没有增加自动清理、镜像导出/加载、远端安装或部署入口。Windows 的管理目录在原生 Windows 下使用同一备份锁；不以 WSL 文件锁冒充 Windows 写入锁。手动副本以清单摘要识别内容，不从目录名推断它们是同一恢复点。

Linux 46 项恢复目录/镜像回归全部通过，Windows 新增 6 项全部通过；另在既有加密测试中补验独立密文点，无需私钥。仅使用临时虚拟文件，无数据库和新容器。路径别名防重补强后已重跑全部上述测试。

## 明确缺口与下一轮顺序

1. 两个早期手动点要求旧镜像 `63ddb3e4…`，不等于当前 `75289115…`。旧镜像仍在云端缓存，本机也有早期镜像缓存/最初搬运包；但尚未以现有严格规则提供归档及OCI/配置ID映射证明。本轮将其判为“缺验证过的依赖”，不是声称镜像已丢失。下一轮优先用已有材料补证明，必要时只在本机新目录整理，不覆盖历史归档。
2. PostgreSQL 运行依赖需要独立完整归档证明。既有冷恢复 `postgres.tar` 仍在，本轮记录文件摘要；本机与云端显示不同内容ID，不能只凭 `postgres:16` 标签认定相同。原冷恢复已成功，不重复开发；下一轮补归档完整校验和ID对应。
3. 当前私密配置存在不等于已形成可携带的完整恢复包。需要明确参数、数据库角色/凭据、私有卷、运维配置的保管对应关系；密码原文或原始包不入Git。格式2密文没有收件公钥指纹，本轮不能单凭元数据证明逐点密钥对应，保留既有完整认证解密证据，后续换钥必须显式记录关联。
4. 实际发布前仍须另行安排空闲窗口、执行时一致恢复点和准确升级范围。本检查不批准部署；正式微信/真机、真实短信及物流服务条件分别保留。

上述结论只针对显式已知目录。有限目录发现不是全盘搜索；其他项目演练、压缩搬运包、旧partial目录均保留，不据此删除。跨机汇总是分次观察，不是跨机原子快照。
