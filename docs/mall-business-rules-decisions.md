# 积分商城业务规则决策记录

- 文档版本：v0.4.0-M1
- 建立日期：2026-08-27
- 最近确认日期：2026-09-01
- 适用范围：M1/v0.4.0 及后续积分商城阶段
- 当前状态：M1 规则、迁移、小程序 API 路由及权限审计基础已建立；尚未实现商城数据库表、业务 API 或页面
- 依据：《业务数据管理 SaaS：旧路线图收口与积分商城新路线图》

## 1. 记录原则

本文件只固化商城开发必须遵守的业务决定，并持续记录尚待产品确认的参数。规则状态分为：

- **已确认**：后续设计和实现必须遵守；
- **待确认**：只有推荐默认值，进入对应阶段前必须书面确认；
- **已替代**：保留历史原因，并指向替代决定。

任何影响现金核销、积分余额、库存、订单、退款或供应商结算的规则变更，都应先更新本文件，再进入独立代码提交；不得用代码实现反向替代业务确认。

## 2. 已确认的产品边界

| 编号 | 决定 | 约束与理由 | 生效阶段 |
| --- | --- | --- | --- |
| MALL-001 | 现金返现与商城兑换是互斥渠道 | 一条业务只能进入一个渠道，防止双重核销；历史业务迁移时默认保持现金返现 | M2 |
| MALL-002 | 现有现金返现行为保持不变 | 商城代码不得改变现有凭证上传、OCR、审核、核销、统计、结算和 Excel 口径 | 全阶段 |
| MALL-003 | 第一版只支持纯积分兑换 | 不做微信支付，也不做“积分 + 现金”混合支付，控制财务与退款复杂度 | M4-M8 |
| MALL-004 | 会员身份绑定微信身份 | `member_public_id` 只能作为公开标识；手机号和车牌号只能用于激活匹配，不能作为永久登录凭证 | M3、M7 |
| MALL-005 | 激活需要额外安全因子 | 微信身份与手机号、车牌号匹配后，还需一次性激活码或短信验证码；必须限流、防枚举和防重复领取 | M3 |
| MALL-006 | 积分使用不可变流水 | 入账、预占、释放、消费、退款、过期和人工调整全部记流水；后台不得直接覆盖余额 | M3-M6 |
| MALL-007 | 积分按批次管理并最早到期优先 | 每次激活形成独立积分批次；消费使用 FEFO，订单保存实际消耗批次 | M3-M5 |
| MALL-008 | 商品与库存管理到 SKU | 商品上下架与库存可售、预占、出库、退回必须以 SKU 为最小业务单位并保留流水 | M4-M6 |
| MALL-009 | 历史订单使用业务快照 | 订单明细保存商品、SKU、图片、积分价、人民币成本、供应商和数量，后续编辑不得回写历史 | M5-M6 |
| MALL-010 | 下单和逆向操作必须原子且幂等 | 订单、库存与积分预占在同一事务完成；提交、取消、退款和发货防重复执行 | M5-M6 |
| MALL-011 | 第一版物流由运营手工录入 | 先记录物流公司、运单号、操作者和时间；一期不依赖收费物流查询 API | M6、M8 |
| MALL-012 | 订单阶段前完成 PostgreSQL 验证 | SQLite 只用于本地开发和少量测试；M5 完成前 PostgreSQL 集成测试必须成为提交门槛 | M1-M5 |
| MALL-013 | 商城后台写操作采用分层授权 | 超级管理员和运营管理员可管理商品、SKU、库存、订单和供应商并生成待确认结算；积分人工调整与供应商结算确认仅允许超级管理员；初审、复核、上传方及无效账号不得获得商城写权限 | M1-M8 |

## 3. 业务参数状态

### 3.1 已确认参数

| 编号 | 参数 | 最终规则 | 确认日期 | 影响与实施约束 |
| --- | --- | --- | --- | --- |
| OPEN-001 | 积分单位与精度 | 保留两位小数；1 积分对应现有业务清单中的 1 金额单位 | 2026-08-27 | 账本、商品积分价和报表统一使用十进制精确值，不使用二进制浮点数计算积分 |
| OPEN-002 | 激活后有效期 | 从实际激活时刻起一个自然年，到次年相同月日、相同时刻过期 | 2026-08-27 | 到期判定统一按 UTC+8；若次年不存在相同月日，则取该月最后一个自然日的相同时刻 |
| OPEN-003 | 激活截止日 | 每个商城积分上传批次独立设置激活截止日 | 2026-08-27 | 超过截止日的未激活权益不得领取；截止日前已激活积分仍按 OPEN-002 独立计算有效期；不得影响现金返现批次 |
| OPEN-005 | 同一会员多条权益 | 允许同一会员持有多个积分批次；各批次独立记录余额与到期日，会员端汇总展示总余额并可查看批次明细 | 2026-09-01 | 会员、积分批次和不可变流水必须保持一对多关系；汇总余额不得覆盖或合并各批次原始余额，到期和 FEFO 消费仍按批次执行 |

| 编号 | 待确认项 | 推荐默认值 | 最迟确认阶段 | 影响范围 |

## 4. 统计与审计不变量

- 现金已核销、商城已激活、商城已消费、未消费余额和已过期积分必须分别统计；
- 同一来源业务不能同时形成现金最终核销和商城积分入账；
- 展示余额即使使用缓存，也必须能由不可变流水重算且结果一致；
- 人工积分调整、库存调整、发货、退款和供应商结算都必须记录操作者、原因和时间；
- 手机号、车牌号、地址和物流信息按最小权限展示，导出和敏感查看需要审计；
- 订单退款必须同步处理订单状态、积分流水和库存流水，禁止只修改文字状态；
- 供应商结算不得纳入取消、未完成或已退款订单。

## 5. 第一版明确不做

- 微信支付和积分加现金混合支付；
- 多商户入驻、自动采购；
- 优惠券、秒杀、拼团和会员等级；
- 依赖收费物流查询 API 的自动轨迹；
- 把第三方开源商城后端直接连接现有业务数据库；
- 仅凭手机号和车牌号登录、领取或扣减积分。

## 6. 决策变更模板

### 2026-09-01：确认会员多积分批次与商城分层权限

- `OPEN-005`：已确认同一会员可以持有多个积分批次，各批次独立记录余额和到期日，会员端汇总展示总余额并可查看批次明细；
- `MALL-013`：已确认超级管理员和运营管理员可管理商品、SKU、库存、订单和供应商并生成待确认结算；积分人工调整与供应商结算确认仅限超级管理员；
- 安全约束：所有商城后台写操作必须使用已登记的审计动作类型并在执行前校验对应细权限；未知动作、未知管理员级别和非管理员账号失败关闭；
- 数据迁移影响：本次只固化权限、审计类型与表设计约束，不执行数据库迁移；
- 现金返现回归影响：无；不修改现有现金返现权限、页面、数据模型、核销或结算行为；
- 专项测试与验收要求：覆盖四类管理员、上传方、空级别、未知级别、全部商城审计动作和未知动作拒绝。

- `OPEN-001`：已确认积分保留两位小数，并沿用 1 积分对应 1 金额单位的推荐口径；
- `OPEN-002`：已确认激活后一个自然年、次年相同月日相同时刻到期；
- `OPEN-003`：已确认每个商城积分上传批次独立设置激活截止日；

## 7. M0 收口与 M1 准入声明

M0/v0.3.0 已作为后续路线的书面基线完成收口。`OPEN-001` 至 `OPEN-003` 已于 2026-08-27 完成业务确认，`OPEN-005` 与 `MALL-013` 已于 2026-09-01 完成业务确认，M1 可以据此进入会员、积分批次与审计结构设计。
