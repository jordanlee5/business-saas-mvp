# 部署发布包与版本核验

2026-11-09，从 `3aa04df` 接续。补齐路线图中“明确提交、文件清单与发布来源核对”的准备工作。这个工具不部署、不连接业务数据库、不访问云账号，也不修改小程序主体。

## 给业务方的说明

服务器就绪后，开发方用已测试、已推送的完整版本编号生成程序包。包里只包含部署所需源码和配置模板，不从电脑工作目录复制真实数据库、上传文件或秘密配置。下载或转移完成后，再按事先单独保留的清单指纹核验；文件、清单或版本不符即停止使用。

秘密资料仍需在服务器私有目录单独配置。发布包不包含会员资料、业务备份或私钥；原本电脑里存在这些文件也不会自动带入。工具会检查选中的 Git 文件里的常见凭据，但这是针对性检查，不是“所有秘密绝不可能漏检”的保证。

## 开发方命令

从包含本工具的受信任源码目录执行。下列 `FULL_COMMIT_SHA`、`RECORDED_MANIFEST_SHA256` 必须换成实际完整值，不能照抄；本工具拒绝 HEAD、短提交号及分支名。

```sh
python3 -m tools.release_bundle create \
  --repo /srv/business-saas-source \
  --revision FULL_COMMIT_SHA \
  --output /srv/saas-releases/new-release

python3 -m tools.release_bundle verify \
  --directory /srv/saas-releases/new-release \
  --revision FULL_COMMIT_SHA \
  --manifest-sha256 RECORDED_MANIFEST_SHA256
```

`create` 只从指定提交的 Git 对象读取，选取 Dockerfile、.dockerignore、依赖清单、alembic.ini，以及 app、migrations、tools、deploy 目录。工作区修改与未跟踪文件不读取。创建前核对所需文件、拒绝符号链接/子模块，使用既有秘密扫描规则；私有文件名和常见密钥命中即拒绝，不输出命中的值。目录必须在来源仓库之外且尚不存在，不覆盖旧版本。写入失败会保留不完整目录，核查后换新目录重做。

成功输出完整提交号、文件数和 manifest_sha256。将这条结果独立保存在受控的发布记录中，不要在传输后重新计算被传输清单的摘要作为“可信值”。`verify` 同时核对可信清单摘要、预期提交、逐文件大小/摘要、缺失或多余文件及符号链接；Linux 上另查可执行位。任何拒绝返回码 1，成功返回 0。

核验通过后才从发布目录构建镜像，并把实际镜像 ID 追加到发布记录。现有恢复工具要求对应备份的原镜像，不用新镜像覆盖历史恢复点。这个文件清单不是密码学签名或依赖锁定；可信记录、来源 Git 仓库、构建依赖及镜像获取渠道仍需保护。操作期间保持输出目录由单一部署账号控制，避免其他写入者在检查后更改文件。

## 范围与后续

本轮使用虚拟 Git 仓库检查排除资料、不可变提交、重复构建、错误版本、符号链接、凭据、缺失/新增/改动文件和清单重写，另从真实仓库的已提交 `3aa04df` 基线生成不含业务数据的部署包做核验。具体构建证据及限制见[验证摘要](validation/release-bundle-20261109.json)。

目标服务器仍需复验依赖下载、实际镜像、HTTPS、受限测试数据、备份与恢复。工具没有执行真实数据迁移、安装定时任务或提交微信审核。
