# 受托发货告知、保存期限演练与本机 UI 验收

2026-10-28。本轮基于 `534f6b6` 开发；功能提交不等于微信审核或真实平台验收。

## 已确认业务决定

会员向本公司兑换商品，供应商仅受托代发。所有对外联系方式统一显示公司客服；供应商公开资料另行确认，不自动公开采购联系人、手机号或内部合同编号。未确认的实际受托方资料不填虚构值。

用户要求短期反复对账，尽量长期保留必要资料。没有确定具体保存天数，也没有授权永久保留所有个人信息。本轮不预设业务天数、不清理真实资料。项目结束后的本地封存属于待设计的独立流程：需确定封存范围、期限、访问负责人、加密与备份、解封条件和最终处理；不能将“本地不调用”当作已删除。

微信昵称/头像声明已由用户删除，6.2已填写。隐私指引只保留本机草稿，不提交审核。正式代码 `APPROVED_PRIVACY_APP_ID` 和 HTTPS 地址仍为空。

## 受托发货功能

会员确认兑换页先通过私有接口 `POST /api/miniprogram/v1/orders/fulfillment-preview` 获取公司、受托方及其负责商品、用途与必要信息范围。所有受托方的联系入口均为公司客服。确认请求包含告知摘要；缺少资料、停用或告知变化时拒绝新订单，要求重新核对。已有订单的幂等重放不受后续资料变化影响。

告知与订单、积分预占、库存预占、收货快照在同一事务中保存。订单详情显示下单时的告知，后续改名或撤销不覆盖历史记录。原有历史订单没有告知快照时不虚构补填。

配置由仓库外 JSON 提供，环境变量为 `MALL_FULFILLMENT_SETTINGS`。文件包含：

| 层级 | 字段 | 用途 |
| --- | --- | --- |
| 根对象 | `operator_name`, `operator_contact` | 已确认的公司名称和统一客服 |
| 根对象 | `suppliers` | 以供应商公开标识为键的对象 |
| 每个供应商 | `name`, `agreement_ref`, `enabled` | 经确认可公开的名称、内部委托依据版本、启用状态 |

配置不接受供应商联系人字段，不读取现有供应商内部联系人作为公开资料。合同引用参与摘要但不下发客户端。无配置时返回未就绪，禁止新下单。上线配置必须与实际委托协议对应；填写 `agreement_ref` 本身不代表协议已经签署。当前没有建立实际供应商配置，因为公开资料仍待确认。

内部 `supplier_packet` 辅助函数只提取当前有效受托方负责的待发货订单资料：收件人、电话、地址、该供应商商品及数量、履约订单标识。它没有开放供应商 HTTP 入口，也不会发送数据。操作者授权、实际提供审计、供应商访问界面及返还/删除凭据尚待后续实现；不能将这个函数说成已完成供应商门户。

## 保存期限与副本清理

`python -m app.privacy_rehearsal --source <SQLite源库> --output <新目录> --policy <规则JSON> --reviews <逐单复核JSON>` 仅通过只读连接备份源库，在新副本上升级和演练。没有真实库执行参数，也没有定时清理任务。报告不含收件人正文；演练数据库仍可能含私人资料，必须保存在受限本地目录，不提交Git。

规则结构为 `version`、`approved` 和 `days`；`days` 必须显式指定 `COMPLETED`、`REFUNDED`、`CANCELLED`。仓库不提供默认业务天数。测试中的短周期仅用于虚拟数据边界验证。终态从完成/退款时间起算，取消订单保守使用最后更新时间。缺少时间、未到期、未批准规则、进行中订单均不允许清理。

每单还须人工核对没有保留要求或未结束售后/争议，提供 `clearance=NO_HOLD_OR_OPEN_CASE` 及与报告一致的 `order` 复核指纹。订单状态或更新时间改变即使复核失效。这是逐单复核约束，不是假称已有完整的争议案件系统。

符合条件时删除独立收货快照，保存最小清理凭据及原请求摘要，保留订单、商品、金额、积分、库存和结算记录。会员和后台将“已清理”与“历史未保存”区分显示；相同请求重试仍返回原订单，不重复下单。本轮仅处理收货快照，不将保留会员关联的交易记录称为匿名数据，也没有清理所有个人信息。

每次演练产生 `report.json` 和 `erasure-receipts.json`。清理凭据应独立受控保存，恢复旧备份后在离线副本使用 `--receipt-journal` 重放，核对终态订单和原请求摘要；冲突或恢复到进行中状态时拒绝。应用遇到清理凭据与收货快照并存时拒绝返回详情，等待离线处理。

这不等于所有旧备份已经清理：恢复时未提供独立凭据仍可能还原旧资料。备份/导出清单、到期销毁、Windows ACL管理、加密封存及恢复操作审计属于后续工作。源库、演练副本和凭据只保存在本机。

## 结构升级边界

新增迁移 `0014_order_privacy`，仅新增 `order_privacy_receipts`、`order_fulfillment_notices` 两表，不回填历史订单。任一新表非空则拒绝降级。

## 本机 UI 验收

在仓库外运行 `python tools/build_ui_demo.py --output <全新目录>` 生成独立小程序项目。导入生成目录到微信开发者工具，使用游客AppID。每页显著显示“离线UI演示”，点顶部入口可切换场景；全部请求和登录由内存虚拟数据响应。生成器检查没有原生网络/登录调用，正式项目隐私标志不变。

1. 正常场景：浏览分类/商品详情，选规格加入购物车，修改数量，前往会员页模拟登录。
2. 查看积分、地址列表；新增/修改/设默认/删除虚拟地址，核对订单地址独立保留的说明。
3. 从购物车进入确认兑换，查看公司客服、多供应商及各自商品、告知；提交后查看订单和积分预占。
4. 控制台推进虚拟履约、发货、完成、退款；回到订单和积分页面刷新。另建一单体验取消。
5. 控制台对终态订单模拟收货资料已清理，查看订单交易信息和告知仍存在。
6. 体验空商品、网络失败、失效会话、受托资料未配置、兑换条件变化、积分不足、提交已成功但响应丢失及查询恢复。

演示图片是程序绘制的占位图。虚拟数据随重新编译重置，控制台也可重置；不要输入真实个人资料。演示项目仅用于本机界面验收，不上传、不发布。

自动客户端检查覆盖服务契约及实际页面脚本串联，不验证微信原生渲染；最终视觉、交互仍由用户在开发者工具确认。控制台模拟后台状态变化，也不替代真实后台操作验收。六项原有正式平台延期继续保留。
