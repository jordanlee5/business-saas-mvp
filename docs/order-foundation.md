# M5-1 订单数据基础

## 范围

M5-1 只建立纯积分订单的持久化边界，不提供下单入口，也不改变积分或库存：

- `orders` 保存会员、稳定订单号、生命周期状态、商品积分总额、人民币成本总额和总数量；一期包邮，因此没有现金或积分运费字段；
- `order_items` 同时保存商品、SKU 和供应商外键，以及下单时的公开编号、名称、供应商 SKU 编码、单位积分价、单位人民币成本、数量和行合计快照；
- `order_points_grant_allocations` 保存订单与原积分批次之间的正数分配证据，为后续 FEFO 消费和原批次退款提供依据。

迁移只创建三张空表，不写入样例或真实业务数据。目录后续改名、换供应商或调价均不得更新历史订单项快照。

## 数据约束

订单积分总额和总数量必须为正，人民币成本总额不得为负。订单项数量和单位积分价必须为正，单位成本不得为负，积分与成本行合计必须分别等于单位值乘数量。同一订单的同一 SKU 只能有一个订单项；同一订单对同一积分批次只能有一条分配记录，分配积分必须为正。

`0007_order_foundation` 直接继承 `0006_inventory_foundation`，保持单一迁移 head。结构就绪检查要求三张订单表和所有关键快照字段真实存在，不能只伪造 Alembic 版本标记。

## 明确不实现

本切片不实现小程序下单接口、订单领域服务、积分预占/消费/退款、库存预占/出库/回补、后台订单页面、供应商结算或任何真实测试数据。分配表的存在不代表已经发生扣分；后续写服务必须把订单、积分和库存变更放入同一事务并完成 PostgreSQL 并发验证。

## 验证与上线

本地可执行 Python 静态编译、M5-1 专项单元测试，以及临时 SQLite 从 0006 升级到 head、`alembic check` 和降级回 0006。真实 PostgreSQL 只能由部署方在独立且可清空、名称以 `_test` 结尾的测试数据库完成迁移往返、外键、数值约束和事务并发验收；SQLite 结果不能替代该证据。
