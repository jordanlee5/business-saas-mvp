# 供应商结算持久化基础说明

## 1. 本切片目标

M6-1 只建立供应商结算的数据库事实边界，为后续批次生成、超级管理员确认、Excel 导出和后台页面提供稳定结构。本切片不会扫描或自动纳入既有订单，也不会改变订单退款行为。

结算口径继续遵循 `OPEN-008`：后续生成服务只能选择生成时仍为 `COMPLETED` 且未退款的订单，结算金额只取订单项已经固化的人民币成本快照。取消、创建、履约中、已发货和已退款订单不得进入结算。

## 2. 批次结构

`supplier_settlement_batches` 表示单一供应商在一个左闭右开完成时间区间 `[period_start, period_end)` 的结算批次，保存：

- 稳定结算公开编号和供应商数据库引用；
- 供应商公开编号、名称快照；
- 结算区间、订单数、订单项数、商品总数量和人民币成本总额；
- 生成管理员、生成时间；
- 确认管理员、确认时间；
- 创建与更新时间。

状态只允许：

- `PENDING_CONFIRMATION`：已生成、等待超级管理员确认；不得携带确认管理员或确认时间；
- `CONFIRMED`：已经确认；必须同时具有确认管理员与确认时间。

批次必须至少包含一个订单、一个订单项和一个商品数量，且 `order_count <= item_count <= total_quantity`。成本总额可以为零但不能为负；生成时间不能早于结算区间结束，确认时间不能早于生成时间。

## 3. 明细快照

`supplier_settlement_items` 每行对应一个订单项，保存：

- 所属结算批次、供应商、订单和订单项引用；
- 订单公开编号和订单完成时间；
- 商品公开编号与名称、SKU 编码与名称；
- 供应商公开编号、名称和供应商 SKU 编码；
- 单位人民币成本、数量与行成本总额。

行成本必须等于单位成本乘以数量。`order_item_id` 使用全局唯一索引，因此同一订单项不能重复进入同一批次或其他批次。目录后续调价、改名或停用不得回写结算快照。

## 4. 迁移与安全边界

`0011_supplier_settlement_foundation` 从 `0010_order_refund_recovery` 线性升级，只创建两张空表和约束，不修改现有订单、积分、库存、上传或现金返现数据。

现有 SQLite 业务库升级前必须：

1. 停止应用并确认源库处于 `0010_order_refund_recovery`；
2. 独立备份数据库文件与 `uploads/`；
3. 运行 `python -m app.migration_upgrade_rehearsal`，只在副本验证 `0010 → 0011`；
4. 审阅副本结构、源库 revision 与业务指纹均未变化后，再单独批准真实库升级。

两张结算表均为空时可以降级回 `0010`；只要存在任一批次或明细，迁移会拒绝降级，避免静默删除结算事实。

## 5. 本切片明确不做

- 不生成结算批次或明细；
- 不确认、撤销或支付结算；
- 不开放结算 HTTP API、后台页面或 Excel；
- 不处理已确认结算后的退款冲销；
- 不改变 M5-6 退款服务和订单状态流转；
- 不引入多商户、自动采购或供应商门户。
