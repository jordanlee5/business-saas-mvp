# 恢复点与镜像归档关联检查

2026-11-12，从 `888662c` 接续。复用已有备份校验和镜像归档校验，增加发布或清理前的只读检查。没有重做镜像导出、加载、冷恢复，也没有安装新定时任务或改变运行版本。

## 当前实现

工具 `tools.staging_recovery_catalog` 遍历显式提供的管理备份目录，验证项目归属、恢复点全量文件清单与摘要；同一编号的跨目录副本必须一致。兼容格式1明文及格式2密文；检查格式2无需私钥，属于密文完整性及依赖检查，不代替认证解密。

每个显式提供的镜像归档只做一次完整校验，包含归档摘要、配置与全部镜像层。由归档真实内容确认 OCI清单ID与经典配置ID映射，不能仅靠标签或清单里未经验证的映射。依此关联恢复点，输出仍被引用的归档与人工复核项。

恢复点盘点前后都使用现有备份锁重新读取并比较，耗时较长的镜像校验不持有备份锁；若中途出现新恢复点、轮换、损坏或锁忙，返回阻断，重新选择空闲时段检查。未知目录、无恢复点、损坏点、不同项目或冲突副本也阻断，不能忽略异常后把旧镜像判为可删。

| 结果 | 含义 |
| --- | --- |
| `required` | 有恢复点或候选发布版本引用，必须保留 |
| `unreferenced_review_only` | 在本次给出的目录范围内未被引用，仅供人工复核 |
| `hold_incomplete_inventory` | 有缺失/损坏/并发变化等问题，不能据此清理任何归档 |

工具永远返回 `deletion_authorized: false`，没有删除、Docker操作或部署入口。它也不会自动发现未提供的备份目录。手动升级前备份、最初部署备份、其他机器或长期封存点必须另行盘点；不能仅凭本轮定时副本目录的通过结果就清理历史镜像。本机私密路径不写入报告，仅使用 `source_1`、`archive_1` 等输入顺序标签。

## 发布与清理前操作

```sh
python3 -m tools.staging_recovery_catalog \
  --project saas-pg-test-example \
  --root <该项目管理备份根目录> \
  --bundle <已保存的镜像归档目录> \
  --candidate-image sha256:<候选发布镜像的完整内容ID>
```

多个 `--root`、`--bundle` 可重复提供。所有恢复点涉及的镜像及候选版本必须被完整归档覆盖才返回退出码0；缺失则返回1。未知新版本未归档时先用已有归档工具准备并核验，再重跑检查。没有新版本发布时省略 `--candidate-image`。

这一步已加入[受限部署操作说明](cvm-first-deployment.md)。通过只代表所给范围的应用镜像依赖完整，不保证数据库升级兼容、业务验收、部署配置/数据库基础镜像或所有灾难恢复材料齐备；不能视作发布授权。本轮没有创建新发布版本，也没有把检查器安装到云端。
