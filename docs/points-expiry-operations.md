# 积分到期维护操作说明（M3-3）

本轮从 `c5239b7` 建立积分到期领域服务和命令入口，沿用 `0003_member_activation_security`，无需数据库迁移。

## 只读预览

在项目根目录、已激活的虚拟环境中执行：

```powershell
python -m app.points_expiry_task
python -m app.points_expiry_task --upcoming-days 30
```

第一条查看当前已到期而尚未关闭的积分批次；第二条查看未来 30 天内到期且仍有可用或预占余额的批次。默认都只读，不扣分、不修改状态、不生成流水，也不自动创建或升级数据库。

时间统一为 UTC+8：已到期使用 `expires_at <= as_of`，即将到期使用 `as_of < expires_at <= as_of + 天数`。一期每批积分从激活时刻起一个自然年有效；查询与任务直接使用激活时已保存的 `expires_at`。

可选参数：

| 参数 | 作用 |
| --- | --- |
| `--account-id 1` | 仅查看指定积分账户；这是账户 ID，不是会员 ID、上传批次 ID 或业务 ID |
| `--limit 100` | 每页 1～1000 个积分批次，默认 100 |
| `--after-grant-id 100` | 从积分批次 ID 100 之后继续，默认 0 |
| `--upcoming-days 30` | 查询未来 1～366 天到期的余额，只读，不能与 `--apply` 同用 |

分页按积分批次 ID 升序，便于按游标遍历；它不是消费 FEFO 顺序。`has_more=true` 表示还有下一页，用返回的 `next_after_grant_id` 继续。一次遍历后，下次任务从游标 0 重新开始，以重新检查曾经受阻的批次。

## 输出含义

| 字段 | 含义 |
| --- | --- |
| `mode` / `query` | `preview` 或 `apply`；`due` 或 `upcoming` |
| `as_of` / `timezone` | 本页固定检查时刻及 UTC+8 时区 |
| `page_count` | 本页查询到的积分批次数量 |
| `page_available_points` | 本页可用余额合计，包含受阻批次，不能解读为已扣减金额或全账户可消费余额 |
| `items` | 本页批次、账户、到期时间、余额、状态及 `block_reason`；不输出手机号、车牌号或激活码 |
| `blocked_count` | 本页不能自动处理的批次数量 |
| `has_more` / `next_after_grant_id` | 是否还有下一页及继续查询的游标 |
| `changed_count` / `expired_points` | 本次实际关闭的批次数量及实际扣减积分，预览均为零 |
| `committed` | 本页是否成功提交；预览始终为 `false` |

当前没有会员积分批次时，`page_count=0`、`blocked_count=0`、`changed_count=0`、`expired_points="0.00"` 是正常结果。仅有商城上传业务、尚未通过激活服务生成积分批次，也会得到空结果。

退出码：`0` 正常完成；`2` 存在阻止项或参数解析不通过（后者会显示用法错误）；`1` 数据库未就绪、运行参数非法或执行失败。不要把退出码 2 当作扣减成功。

## 正式执行

先检查预览，确认数据库目标、到期时刻和数量，并保留执行前备份。正式扣减命令是：

```powershell
python -m app.points_expiry_task --apply
```

这条命令会重新检查当前时刻的候选批次，不会盲目采用之前的预览。一次最多处理一页，当前页有任何阻止项则整页不写入；处理中异常则当前页全部回滚。先前已成功提交的其他页不受后续失败影响。重复执行已完成的批次不会重复扣分。

正常有余额的批次追加一笔负数 `EXPIRE` 流水，来源为 `POINTS_GRANT`，来源编号为该积分批次 ID，固定幂等键为 `points-expiry:<ID>`，原因为“积分批次到期”。同时将该批次可用余额清零、状态置为 `EXPIRED`，相应减少账户余额并增加账户版本。已用尽且余额为零的批次仅关闭状态，不生成零金额流水。来源业务仍为已激活，不会重新开放领取。

阻止项处理：

- 账户或任一同账户批次缓存与流水不一致：先核对账本，不直接改余额掩盖问题。
- 批次冻结：等待冻结业务处理；此任务不自动解冻。
- 存在预占余额：等待关联业务处理；此任务不取消预占或扣减预占积分。
- 尚未完成首笔入账、已用尽却有余额、已过期却有余额、幂等键或流水内容冲突：视为异常数据，失败后核查来源，不能反复强制执行。

## 事务与范围

- SQLite 只读任务显式建立读事务；写任务在候选查询前使用 `BEGIN IMMEDIATE`。两个本机 SQLite 到期任务的竞争处理已纳入独立测试库测试。
- 服务函数 `expire_points_grant` 只 flush，不提交；调用方必须在异常后回滚整个事务。SQLite 的其他调用方也需自行取得写事务。跨多个账户的调用方须按账户 ID 升序锁定，维护任务已经这样处理。
- 到期服务与首笔入账共用“先账户、后积分批次”的锁顺序，取得锁后刷新余额。审计从数据库列读取最新持久化值，不依赖旧 ORM 对象。
- 默认测试不证明真实 PostgreSQL 并发行为。上线该数据库前须在独立测试库完成并发、时区及事务验证；仍遵循 M5 前完成 PostgreSQL 验收的要求。
- 本轮不安装 Windows 计划任务。日后配置定时执行时，应记录标准输出与退出码、遍历所有页，并对非零退出码处理告警。
- 到期任务是记账维护入口，不是消费授权检查。后续订单服务必须在消费/预占事务中实时校验到期时间；未处理的过期缓存不能作为有效余额使用。
- 不修改现金返现、上传承接、凭证、审核、经营统计或数据库结构；人工调整、会员详情及导出后续独立交付。
